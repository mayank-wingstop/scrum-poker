## Overview

This plan initializes the Scrum Poker monorepo with the full technology stack defined in `specs/ARCHITECTURE.MD`. The output is a compilable, testable skeleton — no business logic, no product features. Every item here is prerequisite for F-001.

F-000 has no UI-facing behavior, so Design (Stage 2) and Architecture (Stage 3) are intentionally skipped. This plan goes directly from the feature definition and system/architecture specs to execution.

### Step 2 — Shared types package

**Files to create:**
- `src/shared/package.json`
- `src/shared/tsconfig.json`
- `src/shared/types.ts`

**What to implement:**

`src/shared/package.json`:
```json

  "version": "0.0.1",
  "main": "dist/types.js",
  "types": "dist/types.d.ts",

    "build": "tsc"
```

`src/shared/types.ts` must export the canonical data model from `specs/ARCHITECTURE.MD`:
```typescript
export type CardValue = number | '?' | '☕';

export interface Participant {
  id: string;
  name: string;
  vote: CardValue | null;
  connected: boolean;
}

export interface Session {
  id: string;
  facilitatorId: string;
  currentStory: string;
  deck: CardValue[];
  participants: Map<string, Participant>;
  revealed: boolean;
  createdAt: Date;
}
```

Also export all WebSocket event types from `specs/ARCHITECTURE.MD` as discriminated unions:
```typescript
// Client → Server message types
export type ClientMessage =
  | { type: 'JOIN'; payload: { sessionId: string; name: string } }
  | { type: 'VOTE'; payload: { value: CardValue } }
  | { type: 'REVEAL'; payload: Record<string, never> }
  | { type: 'RESET'; payload: { story?: string } }
  | { type: 'KICK'; payload: { participantId: string } };

// Server → Client message types
export type ServerMessage =
  | { type: 'SESSION_STATE'; payload: unknown }
  | { type: 'PARTICIPANT_JOINED'; payload: { participant: Participant } }
  | { type: 'PARTICIPANT_LEFT'; payload: { participantId: string } }
  | { type: 'VOTE_CAST'; payload: { participantId: string } }
  | { type: 'CARDS_REVEALED'; payload: { votes: Record<string, CardValue> } }
  | { type: 'ROUND_RESET'; payload: { story: string } }
  | { type: 'ERROR'; payload: { message: string } };
```

**Dependency:** Step 1 complete.

## Risk Mitigation

| Risk | Mitigation |
|------|-----------|
| npm workspace hoisting conflicts | Use exact versions in all workspace `package.json` files; run `npm install` from repo root only |
| TypeScript project references misconfigured | Build `src/shared` first; confirm `dist/types.d.ts` is generated before building client or server |
| Vitest / Jest config collision | Keep coverage config in each workspace's own config file; root `npm test` delegates via workspaces flag |
| Playwright failing in CI headless mode | Use `chromium` only; add `--headless` flag in CI env via `process.env.CI` check in `playwright.config.ts` |
| Coverage thresholds too strict for bootstrap stubs | Bootstrap code is minimal; stubs with single-path functions should meet 80% line/function thresholds easily. If not, add simple unit assertions to stub modules |

---

## Rollback Approach

F-000 creates all files from scratch. If the implementation introduces build or test failures that cannot be resolved quickly:

1. Revert the entire branch to the last-known-good commit (the pre-F-000 state, which is just `specs/` files).
2. Re-run from Step 1 with corrections.

There is no production system to roll back at this stage — rollback is purely a git operation.

- [ ] `GET http://localhost:3001/health` returns `{ "status": "ok" }` with HTTP 200
- [ ] No files modified outside `src/**`, `tests/**`, root config files, and `specs/INDEX.MD`

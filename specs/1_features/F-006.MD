# F-006 — Issue Queue (Story Sidebar)

## Context

Real sprint planning sessions involve estimating many stories in sequence. Without a queue, the facilitator must communicate the current story verbally or rely on external tools, breaking the flow of the session. This feature adds a story/issue queue panel to the room: the facilitator can add stories before or during the session, mark them as estimated, and move to the next one — all without leaving the app.

The story queue is purely in-memory and session-scoped. It is not connected to Jira or any external system.

---

## Goals

1. Add a **Story Queue panel** to the room layout (right sidebar on desktop; togglable drawer on mobile).
2. Allow the **facilitator only** to add new stories to the queue (title, up to 200 characters).
3. Display the **currently active story** highlighted at the top of the queue and as the prompt in the main room area.
4. Allow the facilitator to **mark a story as estimated** (moves it to a "Done" section with the agreed estimate value) after a round concludes.
5. Allow the facilitator to **select any story** from the queue to make it the active story, which broadcasts `ROUND_RESET { story: newTitle }` to update all participants.
6. Allow the facilitator to **delete an unestimated story** from the queue.
7. Participants (non-facilitators) can **see the queue** and the active story but cannot modify it.

---

## Non-Goals

- Jira / external tool integration.
- Importing a list of stories from a file (deferred future feature).
- Reordering stories via drag-and-drop (can be added later; queue order is insertion order for now).
- Story descriptions or acceptance criteria beyond a title string.
- Persisting the queue beyond the session lifetime.

---

## User Stories

**US-006-A — Facilitator adds a story**
> As a facilitator, I want to type a story title and add it to the queue so I can plan which items to estimate during the session.

**US-006-B — Facilitator sets the active story**
> As a facilitator, I want to click a story in the queue to make it the current voting topic so participants immediately know what they're estimating.

**US-006-C — Participant sees the active story**
> As a participant, I want to see the current story title displayed prominently so I'm always clear on what I'm voting for.

**US-006-D — Facilitator marks story as estimated**
> As a facilitator, after the team agrees on an estimate I want to log the agreed value against the story and move it to the "Done" list so I can track progress.

**US-006-E — Facilitator deletes a story**
> As a facilitator, if I added a story by mistake I want to remove it from the queue before it becomes the active story.

**US-006-F — Participant views the queue read-only**
> As a participant, I want to see the full story queue (pending and done) so I understand how much is left in the session.

---

## Constraints

- Queue state lives server-side in the session store (added to the `Session` type as `stories: Story[]`).
- Story type: `{ id: string (UUID v4), title: string, estimate: CardValue | null, status: 'pending' | 'estimated' }`.
- Queue changes are propagated to all clients via `SESSION_STATE` broadcast (reusing existing event).
- Only the facilitator can add, select, delete, or mark-as-estimated stories; non-facilitator attempts are rejected with `ERROR`.
- A new WebSocket client message is introduced: `SET_STORY { storyId }` to select the active story (causes a `ROUND_RESET`-equivalent broadcast).
- Story title: 1–200 characters, required.
- Agreed estimate: the facilitator picks a `CardValue` from a dropdown/selector (the values from the session deck); this is stored in `story.estimate`.
- The queue panel has a max visible height with scroll overflow on desktop.
- Mobile: the queue is accessible via a drawer toggled by a button in the header.

---

## Data Model Extension

```typescript
interface Story {
  id: string;          // UUID v4
  title: string;       // 1–200 chars
  estimate: CardValue | null;
  status: 'pending' | 'estimated';
}

// Session extended:
interface Session {
  // ... existing fields ...
  stories: Story[];
  activeStoryId: string | null;
}
```

---

## New WebSocket Events

### Client → Server
| Event | Payload | Description |
|-------|---------|-------------|
| `ADD_STORY` | `{ title: string }` | Facilitator adds a story to the queue |
| `SET_STORY` | `{ storyId: string }` | Facilitator selects a story as active; triggers round reset |
| `ESTIMATE_STORY` | `{ storyId: string, estimate: CardValue }` | Facilitator logs agreed estimate |
| `DELETE_STORY` | `{ storyId: string }` | Facilitator removes a pending story |

All four events are facilitator-only; server rejects with `ERROR` if sender is not the facilitator.

---

## Success Criteria

- A story queue panel is visible in the room layout (right sidebar on desktop; toggle button on mobile).
- Facilitator can type a story title and press Enter or click "Add" to add it to the queue.
- The active story title is displayed as the main prompt in the center of the room.
- Clicking a queued story (facilitator only) makes it active and broadcasts the new title to all clients.
- Facilitator can mark a story as estimated by selecting an estimate value — the story moves to "Done" with the value displayed.
- Facilitator can delete a pending story; it disappears from the queue for all participants.
- Participants see the queue and active story in real time; the Add/Delete/Estimate controls are hidden (not just disabled) for non-facilitators.
- All existing tests pass; new tests cover all four new WS handlers (server) and queue rendering (client).
- Coverage thresholds from `specs/TESTING.MD` maintained.

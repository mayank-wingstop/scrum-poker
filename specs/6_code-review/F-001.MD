### SUGGESTION-1 — Button hover/focus/active CSS states not implemented
**Severity:** SUGGESTION
**Files:** `src/client/src/components/CreateSessionForm.tsx` (submit button, lines ~177–205)

**Description:**
The primary button uses inline React styles. Inline styles cannot express pseudo-classes, so the three interactive states defined in D-105 are not present:
- Hover: `background-color: #4338CA; transform: translateY(-1px)` (D-105)
- Focus: `outline: 3px solid rgba(79,70,229,0.4); outline-offset: 2px` (D-105, AC-004)
- Active: `background-color: #3730A3; transform: translateY(0)` (D-105)

Without a CSS `:focus-visible` rule, keyboard users navigating to the button will see only the browser's default focus ring (or none, depending on browser/OS), which may not satisfy AC-004 (visible focus ring, 3px indigo).

**Spec reference:** D-105 (Button Component States), AC-004 (Focus Ring: `outline: 3px solid rgba(79,70,229,0.5)`)

**Recommendation:**
Add a CSS class (e.g. `.btn-primary`) in `index.css` with the pseudo-class rules. Replace the inline style approach on the button with `className="btn-primary"` supplemented with a conditional for the disabled/loading state. This is the cleanest path given the existing Tailwind/CSS setup:
```css
/* in index.css */
.btn-primary:hover:not(:disabled) {
  background-color: var(--color-primary-hover);
  transform: translateY(-1px);
}
.btn-primary:focus-visible {
  outline: 3px solid rgba(79, 70, 229, 0.4);
  outline-offset: 2px;
}
.btn-primary:active:not(:disabled) {
  background-color: var(--color-primary-active);
  transform: translateY(0);
}
```
This can be addressed in F-002 or as a housekeeping commit — it does not block the landing page from being functional.

### SUGGESTION-2 — Text input focus/hover border not implemented via CSS
**Severity:** SUGGESTION
**Files:** `src/client/src/components/CreateSessionForm.tsx` (name input ~lines 120–145, story input ~lines 165–186)

**Description:**
The text inputs use inline styles for their borders. The D-106 design spec requires:
- Hover: `1px solid #94A3B8`
- Focus: `2px solid #4F46E5` + `box-shadow: var(--shadow-low)`

Neither state is reachable via inline styles. The inputs will show browser-default focus rings only.

**Spec reference:** D-106 (Text Input Component States)

**Recommendation:**
Same approach as SUGGESTION-1 — add `.input-field` CSS class rules with `:hover`, `:focus`, `:focus-visible`, and `:disabled` pseudo-class variants. Addressable in F-002 with the rest of the room UI styling.

### MINOR-2 — Error span uses `display: none` rather than empty content
**Severity:** MINOR
**File:** `src/client/src/components/CreateSessionForm.tsx` (lines ~150–158)

**Description:**
The inline error span toggles visibility using `display: nameHasError ? 'block' : 'none'`. For some screen readers, adding content to a `display: none` element at the same moment it becomes visible may not trigger the `aria-live="polite"` announcement reliably. The ARIA-recommended pattern is to keep the element always visible in the layout (with empty text content) and change only the text — never toggle `display`.

**Spec reference:** AC-003 (`<span id="facilitatorName-error" role="alert" aria-live="polite">`)

**Recommendation:**
Replace `display: none/block` toggling with keeping the span always rendered, and render an empty string when there is no error:
```tsx
<span
  id="facilitatorName-error"
  role="alert"
  aria-live="polite"
  style={{ display: 'block', minHeight: '1.25rem', marginTop: '0.25rem', fontSize: '0.875rem', color: 'var(--color-error)' }}
>
  {nameHasError ? <>⚠️ {form.nameError}</> : null}
</span>
```
This ensures the live region is always in the accessibility tree and will reliably announce the error when content is injected.

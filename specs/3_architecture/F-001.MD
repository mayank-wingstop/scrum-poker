# F-001 — Session Creation: Architecture Specification

**Feature:** F-001 — Session Creation
**Stage:** 3 — Architecture
**Status:** 🔍 Awaiting human review

## 1. Scope

This document defines the component boundaries, integration contracts, and implementation guardrails for F-001 Session Creation. It covers:

- The `POST /sessions` REST endpoint and its integration into the Express server
- The `LandingPage` and `CreateSessionForm` React components
- CSS design token setup in the global stylesheet
- React Router v6 setup in the client entrypoint
- Zustand store additions for session identity
- Rate limiting, input validation, and security controls

This document does **not** re-architect the WebSocket layer, session store shape, or shared type system — those are already settled in `specs/ARCHITECTURE.MD`.

## 2. Components and Responsibilities

### 2.1 New Server Files

#### `src/server/src/routes/sessions.ts`

Single Express router module that owns the `POST /sessions` endpoint.

**Responsibilities:**
- Parse and validate the request body (`facilitatorName`, optional `story`)
- Generate UUID v4 identifiers for `sessionId` and `participantId`
- Call `createSession()` on the session store
- Return `201 { sessionId, participantId, sessionUrl }` on success
- Return `400 { error: string }` on validation failure
- Return `500 { error: string }` on unexpected failures

**Does NOT:**
- Handle WebSocket connections
- Perform authentication or token issuance
- Persist anything to disk or external storage

#### No new server files beyond `sessions.ts` for this feature.

---

### 2.2 Modified Server Files

#### `src/server/src/index.ts`

**Required additions:**
- Import and configure `express-rate-limit` for the `/sessions` route
- Import and register `sessionsRouter` at path `/sessions`

The rate limiter must be applied **before** the sessions router is mounted, scoped only to `POST /sessions` (not to all routes).

#### `src/server/src/store/sessionStore.ts`

**Required addition:** Export a `createSession()` function alongside the existing `Map` export.

```typescript
// Signature contract (implementation detail left to Coding Specialist)
function createSession(params: {
  sessionId: string;
  facilitatorId: string;
  facilitatorName: string;
  story: string;
}): Session
```

The function must:
- Construct a `Session` object conforming to the existing `Session` interface in `@scrum-poker/shared`
- Add the facilitator as the first `Participant` with `vote: null`, `connected: false` (WebSocket not yet established)
- Use the Fibonacci default deck: `[1, 2, 3, 5, 8, 13, 21, '?', '☕']`
- Store the session in the `sessionStore` Map
- Return the created `Session`

### 2.3 New Client Files

#### `src/client/src/pages/LandingPage.tsx`

Route-level component rendered at the `/` path.

**Responsibilities:**
- Render the page shell (`min-h-screen`, centered layout)
- Import and render `<CreateSessionForm />`
- Apply `--color-canvas` background (via Tailwind class or CSS variable)

**Does NOT:**
- Contain form logic (delegated to `CreateSessionForm`)
- Call `POST /sessions` directly

#### `src/client/src/components/CreateSessionForm.tsx`

Stateful form component.

**Responsibilities:**
- Manage form state: `facilitatorName`, `story`, `isSubmitting`, `nameError`, `apiError`
- Implement validation logic (on submit only; reactive error clearing after first attempt)
- Trim `facilitatorName` before validation and before sending to the API
- Call `POST /sessions` via `fetch`
- On success: write `sessionId` and `participantId` to `sessionStorage` (wrapped in try/catch per EC-007), call `useSessionStore`'s setter, then navigate to `/session/:sessionId` via React Router `useNavigate()`
- On failure: surface the API error banner (IB-004 auto-dismiss after 8s)
- Implement the loading state (disabled button + "Creating…" label, IB-003)
- Render the full ARIA attribute set defined in design spec AC-003

**Does NOT:**
- Manage routing configuration
- Manage global CSS tokens

## 3. Data and Control Flow

### 3.1 Happy-Path Sequence

```
Browser                     LandingPage / CreateSessionForm        Express Server
   │                                    │                               │
   │── navigate to "/"  ───────────────►│                               │
   │                          renders form                              │
   │── types name + story ─────────────►│                               │
   │── clicks "Create game" ───────────►│                               │
   │                          validates (client-side)                   │
   │                          sets isSubmitting = true                  │
   │                                    │── POST /sessions ────────────►│
   │                                    │   { facilitatorName, story }  │
   │                                    │                     validates input
   │                                    │                     generates UUIDs
   │                                    │                     createSession()
   │                                    │◄── 201 { sessionId,           │
   │                                    │    participantId, sessionUrl } │
   │                          sessionStorage.setItem(...)               │
   │                          store.setSession(...)                     │
   │◄─── navigate to /session/:id ──────│                               │
```

### 3.2 Error Path (API Failure)

```
                          CreateSessionForm
                                 │
                    POST /sessions → 4xx/5xx/network error
                                 │
                    isSubmitting = false
                    apiError = "Something went wrong. Please try again."
                    (raw server error message NOT exposed)
                    auto-dismiss timer set to 8s
```

### 3.3 sessionStorage Write Contract

| Key | Value | Written By |
|-----|-------|-----------|
| `sessionId` | UUID v4 string | `CreateSessionForm` on success |
| `participantId` | UUID v4 string | `CreateSessionForm` on success |

Both writes are wrapped in a `try/catch`. If `sessionStorage` throws (EC-007 — private browsing), the write failure is silently swallowed and navigation still proceeds.

## 4. API Contract (Server-Authoritative)

### `POST /sessions`

**Rate limit:** 10 requests per IP per 60-second window (express-rate-limit). Response on exceed: `429 Too Many Requests`.

**Request headers required:** `Content-Type: application/json`

**Request body:**
```json
{
  "facilitatorName": "string — 1 to 30 chars after trim, required",
  "story": "string — 0 to 200 chars, optional (omit or empty string)"
}
```

**Success `201 Created`:**
```json
{
  "sessionId": "uuid-v4",
  "participantId": "uuid-v4",
  "sessionUrl": "/session/<sessionId>"
}
```

**Error `400 Bad Request`:**
```json
{ "error": "facilitatorName is required" }
```
or
```json
{ "error": "facilitatorName must be 30 characters or fewer" }
```
or
```json
{ "error": "story must be 200 characters or fewer" }
```

**Error `429 Too Many Requests`:**
```json
{ "error": "Too many requests. Please try again later." }
```

**Error `500 Internal Server Error`:**
```json
{ "error": "Internal server error" }
```

## 5. Security

### 5.1 Input Validation

Server-side validation is the authoritative source of truth. Client-side validation is a UX optimization only — it must never be relied upon as a security boundary.

| Field | Server-side rule |
|-------|-----------------|
| `facilitatorName` | Required. Trim whitespace. Length 1–30 after trim. |
| `story` | Optional. If present and non-empty, length ≤ 200. |

No HTML sanitization is required at this stage (display names and story titles are only shown to session participants within the same session; they are not rendered as HTML by the server).

### 5.2 Rate Limiting

`express-rate-limit` is applied to `POST /sessions` only (not the health route or WebSocket). Configuration:

```typescript
windowMs: 60 * 1000,   // 1 minute window
max: 10,               // 10 session creates per IP per minute
standardHeaders: true,
legacyHeaders: false,
message: { error: 'Too many requests. Please try again later.' }
```

This prevents session-flood abuse from a single IP address.

### 5.3 UUID Generation

Both `sessionId` and `participantId` must be generated using `crypto.randomUUID()` (available natively in Node.js 19+ / available via `uuid` npm package for Node.js 18 LTS). Do **not** use `Math.random()` or any non-cryptographic source.

If `uuid` is already in `package.json` for `src/server`, use `import { v4 as uuidv4 } from 'uuid'`. Otherwise use `crypto.randomUUID()`.

### 5.4 CORS

For local development, the Vite dev server proxies `/sessions` to the Express server. The `POST /sessions` endpoint does not need a CORS header for local dev. If CORS becomes relevant (production), it must be handled at the server level with an explicit allowlist — not wildcard `*`.

### 5.5 No PII Logging

Display names must **not** appear in server logs. Log session creation events as `Session created: <sessionId>` only.

## 6. Reliability

### 6.1 Client Error Handling

The `CreateSessionForm` component must handle all three failure modes without crashing:

| Failure | Handling |
|---------|---------|
| Network error (offline, timeout) | Show error banner; restore button |
| 4xx server response | Show error banner; do NOT expose raw server error text |
| 5xx server response | Show error banner; do NOT expose raw server error text |
| `sessionStorage` write throws | Swallow silently; navigate anyway |

### 6.2 Double-Submit Prevention

The submit button is `disabled` immediately on form submission. The `isSubmitting` flag gates the fetch call — if for any reason the handler is called while `isSubmitting === true`, exit early without calling the API.

### 6.3 Server Store Consistency

`createSession()` must be synchronous. There is no async path in the in-memory store write. The HTTP response must not be sent until the session is fully written to the `Map`.

## 7. Scalability

F-001 introduces one new in-memory store entry per session created. Each `Session` object holds:
- Two UUIDs (strings)
- One `Map<string, Participant>` with initially one entry (the facilitator)
- A `CardValue[]` deck array (9 elements)
- A boolean and a `Date`

Estimated memory per session: ~2–4 KB. At 1,000 concurrent sessions the total footprint is ~4 MB — well within Node.js default heap limits.

The rate limiter (10 creates/IP/minute) prevents burst abuse from a single client. No additional scalability measures are required for F-001.

**Note:** Session TTL eviction (2 hours of inactivity, per `specs/ARCHITECTURE.MD`) is a pre-existing architectural concern — it is not introduced by F-001 and is not in scope here.

## 9. Implementation Guardrails

The following rules are binding on the Coding Specialist (Stage 5). Violations will be flagged in Stage 6 Code Review.

1. **File creation only in defined locations.** Create `src/server/src/routes/sessions.ts`, `src/client/src/pages/LandingPage.tsx`, `src/client/src/components/CreateSessionForm.tsx`. No other new files.

2. **Do not modify shared types.** `src/shared/types.ts` already defines `Session`, `Participant`, `CardValue`, and all WebSocket message types. Do not add or remove fields from any shared type.

3. **No React Router version mixing.** Use React Router v6 API exclusively: `<Routes>`, `<Route>`, `useNavigate()`. Do not use the v5 `<Switch>` or `useHistory()` APIs.

4. **sessionStorage writes are wrapped in try/catch.** See EC-007 in the design spec.

5. **Server validation is server-authoritative.** Client validation is permitted as a UX layer but must not replace server-side checks.

6. **UUID generation uses a cryptographically secure source.** `crypto.randomUUID()` or `uuid` v4. Not `Math.random()`.

7. **Rate limiter scoped to POST /sessions only.** Do not apply it globally. Health and WebSocket routes must not be rate-limited by this limiter.

8. **Error messages surfaced to the user are generic.** The UI shows "Something went wrong. Please try again." for all API errors. Raw server error strings are never forwarded to the browser.

9. **CSS custom properties defined in `src/client/src/index.css`.** No inline styles for design token values. Tailwind utility classes may reference the token values or use equivalent Tailwind classes.

10. **`createSession()` is exported from `sessionStore.ts`.** The route handler imports and calls this function — it does not manipulate the store Map directly.

11. **`autoFocus` is conditionally suppressed on coarse-pointer devices.** Use `window.matchMedia('(pointer: coarse)').matches` to skip autofocus on mobile (IB-001).

12. **Test coverage targets must be maintained.** New server code (`sessions.ts` handler + `createSession()`) must have unit tests using Jest + Supertest. New client code (`CreateSessionForm`) must have component tests using Vitest + React Testing Library. Coverage thresholds from `specs/TESTING.MD` apply.

## 11. Risks and Tradeoffs

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|-----------|
| React Router not in `package.json` | Low | Blocking | Check `src/client/package.json` before coding; add `react-router-dom` if missing |
| `uuid` package not installed server-side | Low | Blocking | Use `crypto.randomUUID()` as fallback (Node 19+); verify Node version |
| `@fontsource/inter` not installed | Low | Visual | Fall back to `system-ui` stack if not available; add to `package.json` if missing |
| `sessionStorage` unavailable (private mode) | Low | Degraded UX | Handled by EC-007 try/catch; acceptable degradation |
| Rate limit too aggressive for dev testing | Medium | Developer friction | Dev environment: set `NODE_ENV=test` and skip the rate limiter in test environments |
| Whitespace-only display name passes server validation if trim is not applied | Medium | Data quality | Server must trim before length check — enforced in guardrail #5 |
